# Mira AI — Frontend Setup Guide

This document explains how to set up, run, build, and deploy the **Mira AI frontend** from scratch, with no prior knowledge of the project. Anyone (client, new developer, DevOps engineer) should be able to follow it independently.

The frontend is a **React Single-Page Application (SPA)**. It talks to the Mira AI FastAPI backend over REST (`/api/v1/...`) and can be served three ways: Vite dev server (development), Docker + nginx (containerized), or as a static bundle served by the backend / any web server (production).

## 2. Prerequisites

Install these on the machine that will build/run the frontend:

| Requirement | Minimum version | Notes |
|---|---|---|
| **Node.js** | 20.19+ (LTS) — **22.x recommended** | Vite 7 requires Node `^20.19` or `>=22.12`. The Docker build uses `node:22-alpine`. |
| **npm** | 10+ | Ships with Node. `package-lock.json` is committed — use `npm ci` for reproducible installs. |
| **Git** | any recent | To obtain the source. |
| **Docker + Docker Compose** | 20+ / v2 | Only needed for the Docker deployment option (Section 7). |

Verify:

```bash
node --version    # v22.x.x (or >= 20.19)
npm --version     # 10.x
```

If Node is missing, install via [nvm](https://github.com/nvm-sh/nvm):

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
nvm install 22
nvm use 22
```

## 4. Environment Configuration

The frontend has exactly **one** environment variable:

| Variable | Purpose |
|---|---|
| `VITE_API_BASE_URL` | Base URL the Axios client uses for every backend call. |

**Important:** Vite env vars are baked in **at build time**, not read at runtime. Changing the value requires a rebuild (`npm run build`) — you cannot change it on a deployed bundle.

Which file is used depends on the Vite mode:

| File | Loaded when | Current value | Meaning |
|---|---|---|---|
| `.env` | all modes (lowest precedence) | `/api/v1` | relative — same origin as the page |
| `.env.development` | `npm run dev` | `https://mira.codsy.ai/api/v1` | dev server calls the live backend directly |
| `.env.production` | `npm run build` | `/api/v1` | prod bundle expects backend on the **same domain** |

Two valid strategies:

1. **Same-origin (recommended, current production setup):** keep `VITE_API_BASE_URL=/api/v1` and make sure whatever serves the frontend also proxies `/api/` to the backend (nginx, or the FastAPI backend serving the SPA itself). No CORS issues.
2. **Absolute URL:** set `VITE_API_BASE_URL=https://your-backend.example.com/api/v1`. The backend must then allow your frontend origin in `BACKEND_CORS_ORIGINS` (see the Backend Setup Guide).

To point the dev server at a **local backend** instead of the live one, edit `.env.development`:

```bash
VITE_API_BASE_URL=http://localhost:8000/api/v1
```

## 5. Local Development Setup (step by step)

```bash
# 1. Get the source (adjust to your repo location / copy the folder)
cd ~/frontend            # or: git clone <repo-url> frontend && cd frontend

# 2. Install dependencies (uses committed package-lock.json)
npm ci
#    (use `npm install` only if you intend to update the lockfile)

# 3. Configure the backend URL for dev (see Section 4)
#    Default .env.development points at https://mira.codsy.ai/api/v1
#    For a local backend: echo 'VITE_API_BASE_URL=http://localhost:8000/api/v1' > .env.development

# 4. Start the dev server
npm run dev
```

Vite prints a local URL — open **http://localhost:5173**. Hot Module Replacement is on: file edits appear instantly without reload.

> **CORS note:** if the dev server (`localhost:5173`) calls a backend on another origin, that backend must include `http://localhost:5173` in its `BACKEND_CORS_ORIGINS`. The Mira backend's default CORS list already includes it.

### Available npm scripts

| Command | What it does |
|---|---|
| `npm run dev` | Start Vite dev server with HMR on port 5173 |
| `npm run build` | Production build → `dist/` (minified, hashed filenames) |
| `npm run preview` | Serve the built `dist/` locally to smoke-test the production bundle |
| `npm run lint` | Run ESLint across the project |

## 6. Production Build (static bundle)

```bash
npm ci
npm run build
```

Output lands in `dist/`:

```
dist/
  index.html
  assets/index-<hash>.js     # bundled app
  assets/index-<hash>.css    # bundled styles
  ...static assets from public/
```

This folder is fully static — deploy it to **any** static host (nginx, Apache, Netlify, S3+CloudFront, or the Mira backend itself). Two rules apply to every host:

1. **SPA fallback:** all unknown paths must serve `index.html` (client-side routing). In nginx: `try_files $uri $uri/ /index.html;`
2. **API reachability:** with the default `/api/v1` base URL, the same host must proxy `/api/` to the backend (port 8000).

Smoke-test the bundle before deploying:

```bash
npm run preview     # serves dist/ at http://localhost:4173
```

### 6.1 Current production deployment (backend-served)

In the current production topology, the **backend API container serves the frontend bundle itself** — no separate frontend server:

1. `npm run build` produces `dist/`.
2. The bundle is synced into `dist-final/`:
   ```bash
   rsync -av --delete dist/ dist-final/
   ```
3. The backend `docker-compose.yml` bind-mounts it read-only into the API container:
   ```yaml
   - /home/usama/frontend/dist-final:/app/frontend/dist:ro
   ```
4. FastAPI serves the SPA and handles `/api/v1/...` on the same origin — which is why `.env.production` uses the relative `/api/v1`.
5. The host nginx (`/etc/nginx/sites-available/mira-api`) proxies port 80/443 → `127.0.0.1:8000`.

So a production frontend update is just: **build → rsync into `dist-final/` → hard-refresh the browser** (no container restart needed; the mount is live). If assets look stale, restart the API container: `docker restart mira_api`.

### 6.2 Netlify option

The SPA also deploys cleanly to Netlify (`mira-ai-f.netlify.app` was used previously):

```bash
npm run build
netlify deploy --prod --dir=dist
```

For Netlify you must build with an **absolute** backend URL (`VITE_API_BASE_URL=https://mira.codsy.ai/api/v1`) and add a `_redirects` file containing `/* /index.html 200` for SPA routing. The backend CORS regex already allows all `*.netlify.app` origins.

## 7. Docker Deployment (self-contained frontend container)

An alternative to Section 6.1: run the frontend as its own nginx container.

The [Dockerfile](Dockerfile) is multi-stage:

1. **Builder stage** (`node:22-alpine`): `npm ci` → `npm run build`, with `VITE_API_BASE_URL` injected as a build ARG (default `/api/v1`).
2. **Runtime stage** (`nginx:alpine`): copies `dist/` into nginx and applies [nginx.conf](nginx.conf), which:
   - serves the SPA with `index.html` fallback,
   - proxies `/api/` → `http://mira_api:8000` (backend container, 300 s read timeout for long pipeline jobs),
   - proxies `/docs`, `/redoc`, `/openapi.json`, `/health` → backend,
   - sets 1-year immutable caching on hashed static assets, gzip on.

### Run it

The backend stack must be up first (it creates the shared Docker network `mira-ai_mira_network` that this compose file joins as external):

```bash
# 1. Start the backend stack first (see Backend Setup Guide)
cd ~/Mira-AI && make up

# 2. Build + start the frontend container
cd ~/frontend
docker compose up -d --build

# 3. Open http://<server-ip>:3000
```

Port mapping is `3000:80` (host 3000 → container nginx 80). To build with a different API URL:

```bash
docker compose build --build-arg VITE_API_BASE_URL=https://api.example.com/api/v1
```

> If the backend uses a different compose project name, the network will be named differently — check with `docker network ls` and update `networks.mira_network.name` in [docker-compose.yml](docker-compose.yml).

## 8. Verification Checklist

After any deployment method:

| Check | How | Expected |
|---|---|---|
| App loads | Open the site root | Landing page renders |
| Correct bundle | `curl -s https://<host>/ \| grep -oE 'index-[A-Za-z0-9_-]+\.js'` | Hash matches your fresh build in `dist/assets/` |
| API reachable | `curl -s https://<host>/api/v1/...` or check browser DevTools → Network | 200/401 responses (not CORS errors or 502) |
| Backend health | `curl -s https://<host>/health` | Healthy JSON response |
| Auth flow | Sign up / log in from the UI | JWT stored, dashboard loads |
| SPA routing | Hard-refresh on a deep link, e.g. `/dashboard` | Page renders (no 404) |

## 9. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `npm run dev` fails with engine/`crypto.hash` errors | Node too old for Vite 7 | Upgrade to Node 20.19+ / 22.x (`nvm install 22`) |
| Blank page after deploy, console shows 404 on `assets/*.js` | Stale `index.html` vs assets mismatch | Redeploy the whole `dist/` (never partially); hard-refresh (Ctrl+Shift+R) |
| API calls fail with CORS errors | Frontend and backend on different origins | Either serve same-origin with an `/api/` proxy, or add the frontend origin to backend `BACKEND_CORS_ORIGINS` and rebuild with the absolute URL |
| API calls return 502 via nginx | Backend container down or wrong upstream name | `docker ps` — ensure `mira_api` is running; check the proxy target in nginx.conf |
| Deep links (e.g. `/reports/x`) 404 on refresh | Missing SPA fallback | Add `try_files $uri $uri/ /index.html;` (nginx) or `_redirects` (Netlify) |
| Changed `VITE_API_BASE_URL` but app still hits old URL | Env is baked at build time | Rebuild (`npm run build` / `docker compose build`) and redeploy |
| Login works but session lost on refresh | redux-persist storage cleared / private-browsing mode | Check browser localStorage isn't blocked |
| Long-running migration requests time out | Proxy timeout too low | nginx.conf already sets `proxy_read_timeout 300s` on `/api/`; keep ≥300 s on any proxy in front |
